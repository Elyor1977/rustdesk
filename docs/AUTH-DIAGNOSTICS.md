# Диагностика сброса после ввода пароля

Это диагностическая сборка, не исправление установленной причины сброса.
Правила входа, проверка пароля, протокол и таймауты не изменены.

## Проверка на двух Windows-компьютерах

1. Отправить локальный коммит обычным `git push origin master`.
2. Дождаться успешных CI и Windows unsigned. Установить новую Windows-сборку
   на оба компьютера; перезапустить их, чтобы служба и интерфейс не остались от
   разных сборок. Постоянный пароль и настройки не сбрасывать.
3. Оставить «Всегда подключаться через ретранслятор», выполнить одну попытку,
   ввести пароль и дождаться ошибки. Записать время. Часы компьютеров могут
   расходиться: сравнивать также последовательность событий, не только время.
4. Сразу после ошибки запустить PowerShell от администратора на каждом ПК:

   ```powershell
   cd C:\Users\Elyor\Documents\ChatGPT\Rustdesk
   powershell -NoProfile -File .github/scripts/collect-auth-logs.ps1
   ```

   Если на другом ПК нет репозитория, достаточно скопировать туда скрипт и
   запустить его по полному пути. Созданный TXT находится на рабочем столе.
   Подписать файлы как клиентский и серверный и передать для анализа.

Скрипт читает активные CURRENT-файлы с FileShare.ReadWrite/Delete, не останавливает
службу и не изменяет конфигурацию. Старые архивы не содержали активный серверный
лог; новая сборка сама по себе эту проблему упаковки не решает. Сборщик выбирает
только auth-diag и записи разрыва, не копирует config. Выходной файл создаётся
только новым, без перезаписи. Если нужный этап отсутствует, это не всегда сбой:
проверить, что запущена диагностическая сборка, и повторить одну попытку после
паузы не менее секунды. Ограничитель глобален для каждого места записи, поэтому
параллельные попытки могут подавлять друг другу строки.

## Маркеры

- client `password_challenge_received`: получен запрос аутентификации.
- client `login_request_send_begin/end ok`: попытка отправить запрос; ok — только
  локальная отправка, не подтверждение приёма сервером.
- server `login_request_received`: запрос дошёл до обработчика; password_present
  — только наличие данных ответа на challenge, не правильность пароля.
- server `password_accepted/rejected`: результат проверки введённого пароля.
- server `authorization_begin/granted`: начало и переход в authorized; granted
  ещё не означает, что клиент получил ответ или первый кадр.
- server `login_error_response`: подготовка ошибки входа, без текста ошибки.
- server `login_response_send_begin/end ok`: отправка ответа, без его содержимого.
- client `login_error_received/login_peer_info_received`: клиент получил ошибку
  либо успешные сведения о принимающей стороне.

Новые строки содержат только фиксированные названия этапов, локальный conn-id и
логические значения. Пароли, их хэши, challenge, salt, ключи, токены, имена,
ID удалённых устройств и полный protobuf не записываются. Каждое место записи
ограничено одной строкой в секунду, с накопленным счётчиком подавленных строк.

## Граница изменений и проверок

`src/client.rs`: только диагностика отправки login-запроса;
`src/client/io_loop.rs`: только диагностика получения challenge/ответа;
`src/server/connection.rs`: только этапы проверки/авторизации и отправка
LoginResponse. Общая отправка остальных сообщений сохраняет прежнюю обработку
результата, но выполняет дополнительную проверку типа сообщения. Нового
состояния соединений, функций авторизации и зависимостей нет.

Rustfmt 1.88 и все 21 тест CI-скриптов, включая статический privacy-контракт,
прошли локально; TLS guard также пройден. Privacy-контракт отверг намеренную
подстановку длины ответа на challenge вместо разрешённого булевого признака;
подстановка удалена перед итоговой проверкой. Сборщик проверен на активных
файлах: прочитаны три CURRENT-файла и получены 16 записей разрыва. В старой
установленной сборке auth-diag ещё нет; это проверка чтения/фильтрации, а не
проверка исполнения новых Rust-строк. Сборщик не меняет установленные файлы.
Компиляция приложения с Flutter остановилась в magnum-opus/scrap из-за
отсутствующего VCPKG_ROOT до проверки изменённых файлов. Эти проверки не
заменяют сборку приложения в CI и воспроизведение сброса на двух устройствах.
