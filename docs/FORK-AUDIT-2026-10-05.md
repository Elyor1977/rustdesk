## Подтверждённые проблемы в изменениях форка

### F1. P2 — подписанный и неподписанный запуск могут отменять друг друга

Источник: `.github/workflows/windows-x64.yml:56–58`, `.github/workflows/android.yml:62–64`.

Группа concurrency не включает `inputs.release`. Для ветки включено `cancel-in-progress`. Поэтому signed/unsigned Windows на одном ref, а Android на одном ref и одной архитектуре попадают в одну группу. Внешняя группа wrapper-workflow не устраняет конфликт внутреннего reusable workflow.

Последствие: запуск, ожидаемый пользователем как независимый, может быть отменён другим запуском. Для Android `all` и `aarch64` — разные группы; обычный push не обязательно отменяет signed `all`.

Минимальное исправление: включить тип сборки в группу; автоматическую отмену разрешать только неподписанным веточным сборкам. Проверка: параллельные ручные signed/unsigned для одного ref и одной ОС.

### F2. P2 — общий CI не проверяет весь Flutter-код

Источник: `.github/workflows/flutter-ci.yml:4`; `.github/workflows/ci.yml`.

Полный Flutter CI запускается только вручную. Основной CI проверяет Linux/Rust, а успешная упаковка Windows/Android не заменяет `flutter analyze` и весь набор Flutter-тестов.

Минимальное исправление: автоматический Flutter job для релевантных pull request/push, с фильтрами путей; сохранить отдельные ручные платформенные сборки.

### F3. P2 — выпуск не зависит от тестов и аудита

Источник: `.github/workflows/release.yml:29,36,44`.

После approval запускаются платформенные сборки, затем публикация. В графе нет обязательного тестового/audit-job. Проверка соответствия версии тегу находится только в publish, уже после дорогих сборок.

Последствие: граф workflow допускает выпуск собирающегося, но не прошедшего проверки коммита. Не проверено, предотвращают ли это внешние правила GitHub.

Минимальное исправление: ранняя проверка версии и обязательный проверочный job до использования ключей подписи. Не дублировать всю сборку второй раз.

### F4. P2 — проверка форматирования текущего пакета не проходит

Воспроизведено Rustfmt 1.88: `--check --edition 2021 --config skip_children=true` для изменённых относительно upstream Rust-файлов.

Несоответствия: `libs/scrap/src/common/aom.rs`, `libs/scrap/src/common/vpxcodec.rs`, `src/keyboard.rs`, `src/privacy_mode.rs`.

Причины: порядок импортов, переносы cfg/выражения и пробел. Изменённые строки текущего пакета могут вызвать отказ fmt-job; фактический набор файлов CI зависит от базы конкретного события. Предупреждение о nightly-only `wrap_comments` само по себе не причина отказа.

Исправление: форматировать только необходимые участки/эти файлы и повторить тот же check. В рамках аудита форматирование не выполнялось.

## Унаследованные проблемы текущего кода

Эти проблемы присутствуют в неизменённых относительно указанной upstream-базы участках. Их нельзя приписывать последнему коммиту форка, но оставлять без оценки тоже нельзя.

### U1. Снято после проверки полного пути — явно разрешаемый TLS fallback

Источник: `src/hbbs_http/http_client.rs:180–224`, асинхронный аналог ниже; `src/common.rs` содержит аналогичные retry-пути.

После ошибки запроса стандартный HTTP-клиент пробует `Some(true)`, что включает принятие недействительных сертификатов; успешный режим сохраняется в TLS-cache. Это используется не только в диагностике: стандартный путь обслуживает API, включая операции аккаунта. Strict-клиенты есть, но не заменяют все стандартные вызовы.

Уточнение: `get_cached_tls_accept_invalid_cert` возвращает `Some(false)`, если пользователь не включил `allow-insecure-tls-fallback`. Поэтому описанный retry с `None` не достигается в стандартной безопасной конфигурации. При явном включении исключения риск подмены сертификата ожидаем и должен быть понятен пользователю; это не доказательство дефекта конфигурации по умолчанию.

Решение: сохранить безопасный default, strict-клиенты и явную настройку совместимости. Удалять её без необходимости означало бы ломать существующие конфигурации с самостоятельно выданными сертификатами. Предпочтителен доверенный пользовательский CA.

### U2. P1 — неопределённое поведение Rust в Режиме 2

Источник: `src/privacy_mode/win_virtual_display.rs:96,109,180,225,242`.

`DISPLAY_DEVICEW` и `DEVMODEW` создаются через `MaybeUninit::uninit().assume_init()` до заполнения полей Windows API. Создание значения с неинициализированными полями нарушает требования Rust; подавление `invalid_value` не делает это безопасным. См. [официальное описание MaybeUninit](https://doc.rust-lang.org/core/mem/union.MaybeUninit.html).

Минимальное исправление: корректная начальная инициализация конкретных WinAPI-структур перед вызовом, без переделки архитектуры конфиденциальности. Проверка: сборка Windows и цикл включение/выключение Режима 2.

Это подтверждённый дефект кода, но НЕ доказанная причина ранее показанного `ret: -1` или размытия картинки.

### U3. P2 — ошибочный прокси заменяется обычным клиентом

Источник: `src/hbbs_http/http_client.rs:76,81,87`.

Если конфигурация/создание прокси не удались, возвращается `Client::new()`. Этот клиент не сохраняет требование использовать заданный прокси.

Последствие: запрос может уйти без настроенного прокси; наличие системного прокси не исследовано, поэтому нельзя утверждать, что он всегда будет прямым.

Исправление: возвращать ошибку вместо обхода пользовательской сетевой политики. Тест: неверная конфигурация не приводит к отправке через запасной клиент.

### U4. P2 — сетевой запрос под глобальной блокировкой OIDC

Источник: `src/hbbs_http/account.rs:149–158`, клиент в `src/hbbs_http/http_client.rs:103–105`.

`ensure_client` удерживает write-lock `OIDC_SESSION` во время синхронного HEAD-запроса. Явного ограниченного таймаута в этом builder нет.

Последствие: медленный/неотвечающий API задерживает операции, требующие той же блокировки, включая обработку состояния сеанса. Это не доказательство блокировки Tokio: проблема именно в длительности владения lock.

Исправление: сетевую пробу выполнять вне lock; задать ограниченный таймаут. Проверка: неотвечающий API не мешает чтению/сбросу состояния.

### U5. P3 — противоречивое сообщение Windows о конфиденциальности

Источник: `src/privacy_mode/win_virtual_display.rs:162–173`.

При `DISP_CHANGE_FAILED` сообщение добавляет `last_os_error`, который может оказаться нулём. Сам `ret: -1` означает отказ; фраза «Операция успешно завершена» относится к другому источнику диагностики и не отменяет отказ.

Исправление: объяснять результат по `DISP_CHANGE_*`; не выдавать GetLastError за достоверное объяснение причины. См. [контракт ChangeDisplaySettingsExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-changedisplaysettingsexw).

Положительные стороны: Actions закреплены SHA; права основного CI ограничены чтением; Windows-подпись проверяет приватный ключ, ожидаемый thumbprint и результат signtool verify; Android проверяет отпечаток keystore и готового APK; временные ключи удаляются. Среди отслеживаемых файлов не обнаружены файлы с расширениями `.pfx`, `.jks`, `.keystore`, `.key`, `.pem`. Это не полное сканирование истории/содержимого на секреты. Настоящие сертификаты, права доступа и настройки reviewers не проверены.

## Известные ограничения, не новые блокирующие findings

- Файловые операции содержат проверки traversal/symlink, `O_NOFOLLOW` и Windows reparse-point handling. Однако проверки родительских каталогов по имени сохраняют документированное TOCTOU-окно (`libs/base/src/fs.rs:562,846,1198`). Это требует локального конкурентного изменения файловой системы; удалённая неавторизованная эксплуатация не доказана. Исправление через handle-relative операции — отдельная задача, не косметический рефакторинг.
- Проверка PE Windows 7 использует список известных несовместимых импортов, а не полную модель всех Win7 API. Она не проверяет все динамические GetProcAddress-вызовы, драйверы, GPU или запуск.
- Windows 7 workflow запускается отдельно; успешная обычная Windows/Android сборка не подтверждает Win7. Режим 2 и современные IDD-драйверы нельзя автоматически обещать для Windows 7.
- Размытие после выхода из Режима 2 не воспроизведено. Нужна корреляция смены дисплея, пересоздания capturer/encoder и состояния video QoS. Нельзя объявлять причиной слабый интернет или найденный UB без измерений.
- macOS/iOS, Linux Wayland/X11, аппаратные кодеки и мобильный жизненный цикл требуют платформенных запусков. Статический аудит не подменяет их.
