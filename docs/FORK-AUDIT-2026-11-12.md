## Подтверждённые ошибки

### 1. P1 — завершение загрузки может опубликовать частичный файл

**Места:** `src/ui_cm_interface.rs:1130–1141,1170–1182`, `libs/base/src/fs.rs:817–848,890–906`, `src/server/connection.rs:3910–3923`.

После ошибки `WriteBlock` принимающая сторона сообщает ошибку, но сохраняет задание. Уже отправленный `WriteDone` вызывает `modify_time()` и безусловно отправляет успех. Этот путь не проверяет сохранённую `write_error`; ошибки `rename` также подавляются. Защита `finish_download()` применяется к другому пути передачи.

В изолированном воспроизведении на настоящей скомпилированной библиотеке `base` исходное содержимое `ORIGINAL_CONTENT` заменилось на `PARTIAL`, хотя `job_error()` уже содержал ошибку. Во втором случае файл был открыт без разрешения переименования: оригинал сохранился, `.download` остался рядом, но ошибка завершения не появилась. Никакие пользовательские файлы не использовались.

Первый сценарий вводит недопустимый номер файла (`FileTransferBlock.file_num`), а не искусственно заполняет диск; он доказывает игнорирование ошибочного состояния финализатором. Ошибка записи/синхронизации устанавливает то же состояние. Очередь IPC допускает получение уже отправленного завершения после ошибки. Реальный двухкомпьютерный сеанс не запускался.

**Происхождение:** дефект есть и в incorporated upstream. Исправления форка защищают скачивание, но не этот путь загрузки на принимающий ПК.

**Исправление:** отдельная завершающая операция для upload с `Result`, отказ от публикации ошибочного задания, передача ошибок переименования в CM; удаление resume-метаданных только после успешного завершения. Два regression-теста: ошибочная передача не заменяет оригинал; заблокированный файл возвращает ошибку.

**Доказательства:** `target/audit-2026-11-12/upload-finalization-repro.rs`, `upload-finalization-build.log`, `upload-finalization-result.txt`.

### 2. P1 — обычные тесты меняют настройки Windows

**Места:** `src/platform/windows.rs:4980–4983`, `src/platform/mod.rs:302–308`; фактическое удаление сертификатов — `src/platform/windows_delete_test_cert.cc:300–397`.

`test_uninstall_cert()` удаляет конкретный тестовый сертификат драйвера RustDesk из настоящих хранилищ. `test_resolution()` меняет разрешение `DISPLAY1` на 2880×1800 без восстановления. Они не помечены `ignore`. Тесты были удалены upstream в `9997b7a3`, но присутствуют снова в форке.

Связанные проблемы изоляции: `src/client.rs:5553` выполняет запросы для публичных ID; `src/common.rs:3410` меняет общий сохранённый rendezvous option; cursor-тесты требуют рабочего стола. Их нельзя считать безопасными автономными unit-тестами.

**Дополнительно воспроизведён P2:** `src/platform/windows.rs:4986–4991`, `test_get_unicode_char_by_vk()` требует `Some('a')` для VK_A. Производственная функция использует раскладку текущего foreground window; на русской раскладке корректно возвращает `Some('ф')`, и тест падает. Он также восстановлен в diff форка. Это ошибка переносимости теста, не неправильная обработка русской клавиатуры приложением. Не менять пользовательскую раскладку ради зелёного теста; тестировать преобразование детерминированно или выделить контролируемую интеграционную проверку.

**Исправление:** убрать возвращённые диагностические проверки из обычного набора либо оставить явными ручными проверками на одноразовой системе. Производственную очистку сертификатов не удалять. В данном аудите эти проверки исключены из прогона.

### 3. P1 — старые ручные workflows обходят правила подписанного выпуска

**Места:** `.github/workflows/flutter-nightly.yml:7–18`, `.github/workflows/playground.yml:31,419–427`, `.github/workflows/flutter-build.yml:1693–1721,1878–1906`.

Ручные Nightly/playground получают signing secrets и могут подписывать APK без prerequisite checks, `environment: release` и проверки `ANDROID_CERT_SHA256`. Отключение расписания Nightly не убирает ручной путь. Наличие ключей в repository secrets и право ручного запуска — необходимые условия; это не доказательство доступности ключей внешнему pull request.

**Исправление:** оставить старые диагностические workflows без production signing secrets либо направить каждый подписывающий путь через общую проверку и подтверждение. Отдельные Windows signed / Android signed сохранить.

### 4. P2 — общий неподписанный workflow теряет Android APK

**Места:** `.github/workflows/flutter-tag.yml:10–15`, `.github/workflows/flutter-build.yml:1707–1730,1892–1915`.

`All platforms unsigned` не передаёт секреты и задаёт `publish-release:false`. Загрузка APK в Artifacts разрешена только при наличии signing key; альтернативный unsigned-путь требует публикации Release. В результате успешная сборка не оставляет доступного APK. Отдельный `Android unsigned` этой ошибки не имеет.

**Исправление:** добавить сохранение неподписанного результата в Artifacts для split и universal APK; отсутствие ожидаемого файла должно завершать job ошибкой.

### 5. P2 — пароль Android-keystore искажается при записи key.properties

**Места:** `.github/workflows/android.yml:229`, `flutter/android/app/build.gradle:14`.

Секреты записываются через `printf '%s'` без Java Properties escaping. `Properties.load(InputStream)` интерпретирует обратные слеши, удаляет начальные пробелы значения и читает байты как ISO-8859-1. Например, буквальный пароль `abc\def` превращается в `abcdef`: проверка keytool с исходной строкой может пройти, а Gradle-подпись — упасть.

**Исправление:** читать signing values из окружения непосредственно в Gradle либо корректно сериализовать Java Properties. Пароли пользователя не читались; заключение основано на коде и формате, без реальной подписи.

### 6. P2 — жест запускается после закрытия экрана

**Место:** `flutter/lib/common/widgets/gestures.dart:138–175`, отсутствует очистка таймеров в `dispose()`.

Widget-тест: pinch → поднять палец → переместить оставшийся → удалить виджет → подождать 250 мс. После удаления неожиданно вызывается `onOneFingerPanStart`. Производственный callback удерживает старый BuildContext и может инициировать ввод. Сам callback после удаления воспроизведён; отправка события на реальный удалённый ПК не проверялась.

**Происхождение:** исходная проблема debounce есть upstream; форк добавляет ещё один таймер без очистки.

**Исправление:** отменять `_debounceTimer` и `_resetTimer` в `dispose()`; один widget regression-тест. Доказательство: `target/audit-2026-11-12/gesture-widget-disposal-probe.dart` и `.log`.

### 7. P2 — опрос состояния соединения выполняется параллельно

**Места:** `flutter/lib/desktop/pages/connection_page.dart:55–57`, `flutter/lib/common.dart:2930`.

Callback таймера теряет Future `updateStatus()`, поэтому защита форка от наложения вызовов не работает. Widget-тест с незавершённым первым запросом воспроизводит второй запрос через секунду. Медленные ответы способны накапливаться и приходить в устаревшем порядке.

**Происхождение:** вызывающий код унаследован; защита periodic helper в форке применена не полностью.

**Исправление:** `await updateStatus()` и один тест с задержанным ответом. Доказательство: `target/audit-2026-11-12/status-overlap-probe.dart` и `.log`.

## Подтверждённые пробелы CI и платформенная граница проверки

- **P2, пути запуска CI:** `.github/workflows/windows-x64.yml:20–40` и `android.yml:30–48` не покрывают ряд настоящих входов сборки: `build.rs`, `.cargo/**`, `vcpkg.json`, `res/vcpkg/**`, patch/script dependencies. Изменение только overlay дополнительно исключено общим CI на push. Возможен зелёный commit без нужной платформенной сборки. Добавить пути с проверкой конкретных примеров в существующий contract-test.
- **P2, тесты перед подписью Windows:** `release-checks.yml:10–18` запускает Linux CI и Flutter VM. Windows Rust-тесты в `flutter-build.yml:379–389` доступны через другой, ручной Full Flutter CI, а `windows-x64.yml` их не вызывает. Добавить безопасные тесты release features перед подписью; сначала устранить проблему №2.
- **P2, Linux sleep inhibition:** `src/platform/linux.rs:2921–2966` заменяет владеющий ресурсом handle на `systemd-inhibit ... sleep infinity`. Только `Drop` убивает процесс; SIGKILL/abort обходят Drop. Дочерний inhibitor может пережить RustDesk и продолжить блокировать сон. Владение процессом проверено по коду, Linux/systemd эксперимент не выполнялся. Предпочтителен logind Inhibit через уже имеющийся DBus с принадлежащим RustDesk FD. [Поведение systemd](https://github.com/systemd/systemd/blob/main/src/login/inhibit.c).
- **P3, форматирование:** проверка Rust 1.88 всех 221 изменённых относительно общего предка `.rs` обнаружила отличия в четырёх файлах: `libs/scrap/src/wayland/display.rs`, `src/server/login_failure_check.rs`, `src/server/port_forward_mux.rs`, `src/server/video_qos/tests/invariants.rs`. Последний push успешно прошёл свой меньший набор файлов. Это отложенный дефект форматирования, не ошибка текущей сборки. Исправлять отдельным небольшим commit, без массового форматирования проекта.

## Что оптимизировать

1. **Убрать лишние bridge jobs.** `bridge.yml` генерирует два варианта Flutter bridge. Android и Windows x64 используют один, но ждут оба. Явный выбор нужных вариантов сократит работу CI и зависимость от неиспользуемого job; время экономии без сравнительного прогона не заявляется.
2. **Проверять signing inputs до дорогой компиляции.** Наличие и соответствие сертификата/keystore проверять ранним шагом внутри защищённого signed job. Финальную проверку подписанного APK/EXE оставить.
3. **Устранить наложение status requests** из пункта №7: это уже измеренное лишнее обращение, а не предположение об ускорении.
4. **Профилировать видео до изменения алгоритма.** Измерить число YUV→RGB преобразований, длину очереди событий и время восстановления качества после Режима 2. Сохранить исправления времени жизни decoder-owned buffers. Аудит не установил причину прежнего размытия и сбросов соединения.
5. **Сокращать сопровождаемый diff по назначению.** Около 16 тысяч добавленных строк приходятся на vendored DTLS. Нужен отдельный реестр его небольших собственных patches; нельзя возвращать старую криптографию ради уменьшения diff. Опасные и пустые возвращённые диагностические тесты стоит отделить от полезных regression-тестов. Переписывание истории для уменьшения счётчика коммитов не исправляет код.
6. **Разобрать async UI diagnostics по достижимости.** Из 292 info анализатора 28 связаны с BuildContext после await. Проверять жизненный цикл адресно; не считать каждое замечание отдельным подтверждённым багом и не применять массовый autofix.
