## TLS и проверяемое исключение аудита

Через Cargo обновлены только связанные пакеты:

- `rustls-webpki`: 0.103.14 → 0.103.16;
- `webpki-root-certs`: 1.0.3 → 1.0.10;
- `webpki-roots`: 1.0.9 → 1.0.10.

Сохранены `rustls 0.23.46`, `rustls-pki-types 1.15.1` и закреплённые Git-зависимости. Cargo дополнительно нормализовал одну ссылку на уже присутствующий windows-targets; новые Windows-пакеты не добавлялись. Lockfile не правился вручную.

Причина обновления: [RUSTSEC-2026-0381](https://rustsec.org/advisories/RUSTSEC-2026-0381.html), [0382](https://rustsec.org/advisories/RUSTSEC-2026-0382.html), [0383](https://rustsec.org/advisories/RUSTSEC-2026-0383.html). Это сертификаты TLS-соединений, не ключи подписи Windows/Android.

Обычный `cargo audit` после обновления всё ещё сообщает одну запись 0381 для `webpki-roots 0.26.11`. Проверен исходный код опубликованного пакета: он только переэкспортирует `parent::TLS_SERVER_ROOTS`, а parent теперь разрешён в исправленный 1.0.10.

Глобальные исключения `.cargo/audit.toml` не расширялись. Только шаг CI перед `cargo audit --ignore RUSTSEC-2026-0381` запускает fail-closed проверку `.github/scripts/check_tls_roots.py`:

1. Все реальные хранилища webpki-roots должны быть исправленной registry-версией 1.x не ниже 1.0.10.
2. Исключение допускает только registry-обёртку 0.26.11 с точной проверенной контрольной суммой.
3. Её единственная зависимость должна указывать на присутствующее исправленное хранилище.
4. Любая другая старая версия, источник, checksum или зависимость прерывает CI до исключения advisory.

Два теста проверяют допустимую обёртку и отказ на небезопасных вариантах. Дополнительная мутация проверки checksum в памяти была обнаружена тестом; исходник при эксперименте не изменялся. Контракт CI проверяет порядок guard → audit.

Итог с этой проверкой: **0 неисключённых записей уязвимостей**. Остаются **27 предупреждений**: 24 unmaintained и 3 unsound. Они не объявляются устранёнными. Необработанный результат аудита с одной записью обёртки также сохранён локально. База RustSec: `e6f94f3`.

## Согласование защит передачи файлов

Конфликты в `libs/base/src/fs.rs` и `src/client/io_loop.rs` разрешены с сохранением проверок форка, не заменой файлов целиком.

- `open_for_write` сохранена без изменения. Возобновление в новом `fs/download.rs` использует эту функцию, не следуя финальной symlink/reparse point.
- Сохранены `resume_error`, `write_error` и отказ продолжать запись после необратимой ошибки.
- Новое ожидание согласия на перезапись выделено в локальный тип ошибки `NeedsConfirmation`: оно допускает подтверждение и продолжение. Ошибки записи не маскируются под это состояние.
- После ошибки записи `finish_download` отказывает в публикации частичного файла. Добавлен тест: данные остаются в `.download`, итоговый файл не появляется.

- Ошибки получателя теперь сразу сообщаются интерфейсу и отменяют передачу, а не только записываются в лог.
- В Windows-шаг полного Flutter CI добавлен `-p base`: корневой `cargo test --lib` не запускает тесты зависимого workspace-пакета.

Не добавлялись новые поля состояния, таймеры, кеши или общие интерфейсы сверх самого upstream. Добавленный тип ошибки нужен только для разграничения подтверждения и настоящего сбоя записи.
